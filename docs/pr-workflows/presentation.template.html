01 · Product boundary

Fix and push automatically.
Let a person merge.

  1. A team PR becomes activeA poll or saved timer wakes the daemon. Draft and closed PRs stop new work.
  2. The engine clears routine blockersRepair conflicts and actionable reviews. Test the candidate and conditionally push to the PR branch.
  3. Fresh evidence determines the handoffMissing evidence, product choices, exhausted attempts, and ready-to-merge work get different packets.

First-release boundaries

  • Engineers own the process and its permitted actions.
  • Same-repository repair is the first pilot. Fork repair needs its own policy.
  • The engine has no merge operation available in v1.
  • Local test mode works with the developer's supported CLI account.

This is a proposed system. The editor here is a fictional concept. Local agent chat and its visible edits are planned v1 features, not implemented in this mockup.

02 · State model

A PR can have several facts at once.

A young PR can also have a conflict and an unresolved review.

openage 7 minconflictunresolved thread

Keep these as independent observations. The evaluator chooses one next action using explicit precedence.

Unknown mergeability or an incomplete review read is missing evidence. It must never become “clear to proceed.”

  1. Lifecycle and evidence firstClosed → stop. Draft → park. Incomplete facts → refresh. New head → debounce.
  2. Repair the current blockerConfirmed conflict, then actionable review. Suppress unchanged concerns already handed to a human.
  3. Wait, analyze, or hand offBound bot-activity waits. Classify and review this head. Send a packet only when its decision evidence changes.

Who computes it? What may it change?

Use “analysis action,” “workspace action,” and “external effect.” Deterministic code can perform a high-impact write; an agent can return data without one.

Triage is a process containing these actions. Producing a classification and applying its labels are separate operations.

04 · C4 level 1

The service sits between signals and decisions.

@@CONTEXT@@

The local CLI, Electron editor, and private daemon are independent applications. GitHub owns PR facts and merge policy; the daemon owns progress, budgets, and receipts. Narrow screens can scroll the diagram horizontally.

05 · C4 level 2

Separate repository execution from credentials.

@@CONTAINERS@@

The daemon also collects GitHub evidence. The CLI connects to its model provider through a separately controlled path. The broker can begin as a daemon module, but never runs inside the PR worker. Full relationships are in architecture.md.

06 · C4 level 3

A small control loop with explicit responsibilities.

@@COMPONENTS@@

These are responsibilities, not a requirement for six packages. The pure evaluator makes recorded-fixture replay possible without GitHub or a model call.

07 · Runtime progress

Waits are durable state.

@@STATE_MACHINE@@

Artifact-only results return to observation. Close, draft, lease loss, and revocation are checked at every checkpoint. A previously dispatched remote write must be reconciled.

Persist the deadline, release the lease, and stop an idle worker. A daemon restart must not forget a review wait.

08 · Autonomous repair

Prove the target again before a push.

@@SEQUENCE@@

If the remote ref changed from H1, reject the request and reobserve. If the connection fails after submission, read the ref before retrying. A local fencing token cannot revoke a write GitHub already accepted.

09 · Authoring and durable data

Text files you can edit.
Control state an agent cannot rewrite.

team-pr/
  workflow.json
  prompts/
    review.md
    classify.md
    address.md
    resolve-conflict.md
  editor.json   # optional layout

private-runtime/pr/<id>/
  state.json    # engine export
  notes.md      # agent context
  artifacts/

Three different authorities

  1. Trusted immutable process packages define behavior. Pin JSON and referenced Markdown before each run.
  2. The database commits control state, timers, budgets, and effects. state.json is a revisioned projection.
  3. notes.md is bounded, revisioned working context. It cannot grant a permission or schedule work.

One JSON file per PR can be enough for a strictly local single-process tool. A daemon benefits from database transactions across work, timers, and effect receipts.

10 · Structured outputs

Validate the format, then verify the evidence.

  "headSha": "…pinned head…",

Abbreviated illustration. Full schemas and valid examples are included in the documentation packet.

  • Reject extra fields and unsupported enum values.
  • Check source locations against the exact head and base.
  • Attach test receipts from the host, not the model's claim that tests passed.
  • Represent blocked and no-change repairs without inventing a commit.
  • One bounded schema-repair retry, then a visible block.

An acceptable review is advisory. Current required checks, coverage, policy, and unresolved concerns determine readiness.

12 · Reliability

The difficult moment is after the remote write.

FailurePersist before actingRecover by checking
Repeated observationObserved revision and due PRRetain progress; coalesce the wake
Worker loses its leaseFencing token and attempt identityReject stale local output and new broker requests
Push succeeds, reply is lostExpected old SHA, candidate SHA, target refRemote ref equals candidate, old head, or an unexpected value
Message delivery is uncertainLogical request ID and destinationDestination message or explicit unknown outcome
Process upgraded during waitPinned definition and existing receiptsExplicit migration; unchanged intent keeps its receipt

Signals may be delivered more than once. Exactly-once GitHub writes are not a general guarantee. Each effect needs its own precondition and reconciliation rule.

13 · Reliable work for trusted teams

Trust the team. Bound the automation.

Keep the daemon working

  • Pin workflow JSON and referenced review Markdown from one commit.
  • Reject invalid updates and keep the last working configuration.
  • Keep runtime state, notes, and generated results outside Git.
  • Stop attempts at their deadline and clean up child processes.

Stop repeated work

  • Own commits do not reset repair or spending limits.
  • Suppress unchanged concerns and no-progress repairs.
  • Recheck the head before pushing the tested commit.
  • Reconcile uncertain writes instead of repeating a repair.

Repository instructions and PR authors are trusted. Hostile-code isolation is outside v1. A configuration PR may use its own proposed review instructions in a pinned local trial.

14 · One VM first

Keep execution separate from scheduling.

ResponsibilityV1Later options
SchedulingOne Linux daemon, durable timers and leasesCoordinated schedulers or managed orchestration
ExecutionBounded CLI processes and disposable checkoutsWorkers on multiple VMs or Kubernetes
Durable dataSQLite and private local filesShared transactional database and object storage

The VM is a v1 failure point and throughput limit. Serialized job inputs, logical artifact IDs, and persisted receipts make later distribution possible. Cloud functions still need a compatible execution environment for Git, tests, and provider CLIs.

15 · Budget model

Reserve the budget before the work starts.

120 units / day

Illustrative arithmetic, not provider pricing. Units can map to known API usage. Subscription limits still need hard attempt and runtime ceilings.

  • Deduplicate signals and cache by complete input digest.
  • Use deterministic rules before an agent when they give the answer.
  • Reserve per-PR and daily budgets transactionally.
  • Cap total repairs across new heads, not only per head.
  • Stop unchanged findings and no-change repair loops.
  • Persist long waits and release expensive workers.

16 · Bring someone in with a specific decision

One current request. Evidence in a known format.

example-org/sample-app · PR #42 · head ccccccc

Ready for human merge

The requested ownership check is pushed. Current required tests pass; the review has no blocking findings.

Decision
Inspect the authorization change and merge if the evidence is sufficient.
Changed
Ownership validation and a regression test.
Evidence
Current review, two test receipts, confirmed push, addressed thread.
Uncertainty
Production authorization configuration was not verified.
  • Use explicit outcomes: needs author, needs team, ready for human merge, or blocked execution.
  • Route by policy over validated classification. Agents cannot pick destinations or mentions.
  • Use rich Slack channel messages or author DMs, with GitHub links and the CLI inbox for full evidence.
  • Supersede stale requests when the head or relevant evidence changes.

A message or eyes reaction is not permission. V1 uses GitHub for the actual human merge.

18 · Fast iteration without surprise

Commit valid files. Keep running jobs pinned.

Edit files / graph→Validate→Replay + compare→Review impact→Auto-activate valid commit

One executable format

  • Stable IDs and ordered rules.
  • Markdown referenced by relative path.
  • Optional layout excluded from behavior digest.
  • Unknown schema version opens read-only.

Waiting PRs keep their version

  • Watch a configured branch; keep the last valid package on errors.
  • Migrate existing PRs at a recorded checkpoint.
  • Retain logical effect receipts across equivalent versions.
  • Rollback holds until the operator resumes automatic activation.

Rollback changes future execution. It cannot undo a pushed commit or a delivered message.

Start with a narrow interpreter and SQLite. Reconsider a durable runtime when operating recovery costs more than the dependency would. These are design inferences from the linked primary sources.

20 · Repo Chap

One product. Three applications.

  • repo-chap CLI for local trials and daemon operations.
  • Electron app for local editing, agent collaboration, and simulation.
  • Linux daemon for GitHub polling, bounded work, and Slack delivery.

CLI and Electron target macOS and Linux. The daemon uses a GitHub App on a VM without public ingress. Workflow evaluation and validation are shared.

  1. Prove local behaviorValidate, replay, and inspect before enabling remote effects.
  2. Prove recoveryTest restarts, stale heads, invalid config, and uncertain writes.
  3. Run the personal pilotReview, repair, and send readable channel/DM handoffs. People merge.

Daily repository care and distributed deployment are later refinement. Keep scheduler, worker, and storage responsibilities separate without building those deployments in v1.
